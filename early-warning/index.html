Student early warning: a deployed model you can use

At the start of weeks 2, 4, 8 and 12 of a module, the model gives every enrolled student a risk: the probability that they end the module with Fail or Withdrawn. Advisors get the top 20% of each module as a list, with reasons, and decide whom to contact first.

The data is the public Open University Learning Analytics Dataset (OULAD), presentation 2014J, which the model never saw in training. This is a worked example of deploying a model, which I use in my teaching. Below is the tool first, then how each part of it is built.

How it is deployed, piece by piece

        
this page ──▶ proxy (Cloudflare Worker) ──▶ HTTP API ──▶ Lambda (container) ──▶ model files

            weekly batch job (same container) ──▶ risk lists in a private S3 bucket

        

            

                
Batch and real-time scoring

                
The batch job scores every student in each module and keeps the top 20%. It is started by hand here; in a teaching period a weekly schedule would start it. A list like this needs the whole module, so it cannot come from scoring one student at a time. The lists on this page were made the same way, by an export script that scored the whole 2014J cohort once through the live API.

                
The student record uses real-time scoring: one row in, one risk and its reasons out, through the API.

                
batch.py · score.yml · demo_export.py

            

            

                
The API and its container

                
A FastAPI service with two routes, GET /health and POST /v1/score (1 to 500 students a call). Pydantic rejects unknown fields, so a demographic field cannot reach the model, and rejects rows that cannot occur, such as more late submissions than submissions.

                
The same container image runs the API on AWS Lambda and the batch job. It holds the runtime libraries only, runs as a non-root user and is scanned for known vulnerabilities in CI.

                
api.py · Dockerfile

            

            

                
Access: IAM and GitHub OIDC

                
There are no AWS keys anywhere. GitHub Actions signs in to AWS with a short-lived OpenID Connect token, and each job gets a role that can do only that job: the deploy role cannot read the risk lists, and the scoring role cannot change the service.

                
infra/foundation

            

            

                
CI/CD and retraining

                
Every pull request and every push to main runs the tests, a secret scan, a container build and scan, and Terraform checks. Retraining is a manual workflow: it reruns the whole chain from the raw data, stops if any saved result changes, then builds, scans and deploys the image and calls the live API.

                
ci.yml · retrain.yml

            

            

                
Monitoring and drift

                
Each batch run compares the new cohort's inputs and scores with the training cohort using the Population Stability Index (PSI): below 0.1 is stable, 0.25 or more is a major shift that a person reviews. After the module ends, the lists' recall is checked against what was expected.

                
drift.py · monitoring_report.md

            

            

                
Leakage guard

                
A prediction at the start of week 8 may only use data dated on or before the day before week 8. The feature query cuts every click and submission at that day, and drops students who had withdrawn by then, so the model never sees the future it is asked to predict.

                
student_week.sql

            

            

                
This page's proxy

                
The page does not call AWS directly. A small Cloudflare Worker checks each request first: JSON only, at most 8192 bytes and 5 students, known fields only. It allows 60 calls a minute from one address and 240 a minute to AWS in all, under the API's own throttle of 5 requests a second (bursts of 10).

                
CORS lets browsers call it only from this site and a local test server; curl and Python, which send no Origin header, are served as normal.

                
proxy/src/index.ts

            

            

                
Caching

                
The advisor lists are scored once and served as static files, the cheapest cache there is. The page also remembers each answer it already has during your visit: send the same row twice and the second answer comes from memory, which the HTTP panel says.

                
There is no cache in the proxy: Cloudflare's cache API does nothing on a workers.dev address.

Limits and fairness

        
A list of 20% cannot reach everyone. At week 8 the list reached 0.4135 of the students who went on to fail or withdraw, and 0.7958 of the students on it did. At week 2 the model is no better than ranking by fewest clicks (recall 0.3092 against 0.3139), and it over-predicts for the whole cohort that week by 0.0621.

        
Groups are not reached equally. At week 12 the list reached 0.4132 of at-risk women and 0.4742 of at-risk men. Gender, age, region, education, deprivation and disability are not inputs, but leaving them out does not make a model fair by itself, so the audit checks outcomes by group.

        
A reason is not a cause. Reasons say which inputs raised this student's score in this model. The model sees clicks and submissions only, nothing of work, caring duties or health. A person decides what happens; the list is a prompt to offer help, not a judgement.
