How it works

Ask My Papers, from PDF to cited answer

The engineering behind the research assistant on my home page: how it reads papers, finds the right passages, writes an answer it can back up, and how I check that it keeps doing so.

Reju Sam John Auckland, New Zealand October 2026 Try it on my papers →

The chat on my home page is not a demo built for this site. It is the embed of Ask My Papers, a product I build at Tasman Lab. A researcher adds their papers and gets an assistant that answers questions from those papers only, and points to the page of the PDF each claim came from. When the papers don't cover a question, it says so instead of guessing.

This page describes how it works. It is written for people who build or hire for this kind of system, so it goes into the design decisions and the failure modes, but it leaves out the exact tuning values, which are the part that took longest to get right.

1. What it is

A researcher signs up with an email address and adds papers in whichever form they have them: a DOI, an arXiv identifier, or a PDF upload. A few minutes later they have an assistant with its own public page. Visitors ask questions in plain language and get a short answer with a list of the papers it drew on, each with the PDF page number.

The same assistant can then be placed wherever people meet the researcher's work:

  • an inline chat in an iframe, which is what sits in the hero of my home page;
  • a floating button that opens the chat in a panel, also on my home page;
  • a badge and a QR code for profiles, slides and posters;
  • an email signature line.

Each researcher gets a private kit page with these snippets ready to copy. The embeds set no cookies, and the button script is versioned and frozen once published, so a site that pins it with a subresource integrity hash never breaks.

There is also a private library: a second, separate collection for the papers a researcher reads rather than writes. Only they can see it or ask it. They can search their reading, their own papers, or both together, and a citation opens the stored PDF at the cited page. It is in early use with a small group of researchers before it opens to every Pro account.

Everything runs on Cloudflare: one Worker for the pages, the API and the embeds, D1 for records, R2 for files, Queues for background work, Vectorize for vectors, a Container for heavy PDF reading, and AI Gateway in front of every model call. Each assistant's passages live in their own Vectorize namespace, and every search result is checked against the assistant's ID prefix before it can reach a prompt, so one researcher's papers can never answer another's visitors.

2. Reading papers properly

Retrieval can only be as good as the text it searches. The first version of this system pulled plain text out of PDFs, and for my epidemiology papers that was mostly fine. Then a mathematician tried it. Plain PDF text turns equations into scattered symbols, flattens tables into runs of numbers and loses which heading a paragraph sits under. Questions about a theorem or a model's parameters came back vague or wrong. So reading became its own pipeline.

A queue, not a request

Reading a long paper precisely can take minutes, far longer than a web request should wait. When a paper is added, the Worker fetches it if needed (arXiv directly, a DOI through an open-access lookup), stores the PDF in R2 and puts a job on a Queue. A consumer takes papers one at a time, with a little parallelism, and moves each job through queued, reading, indexing and ready. The sign-up page polls those states, so the researcher watches each paper go through, with a plain reason if one is refused (a scanned PDF with no text layer, for example, or one over the page limit).

Failed jobs are retried with growing delays, and a job that still fails cleans up any passages it wrote. An hourly sweep catches jobs whose queue messages were lost. After a paper attaches, a follow-up check asks Vectorize whether the paper's first passage is actually searchable yet, because a vector index is eventually consistent and "written" is not the same as "findable".

Three ways to read, best first

  • The author's LaTeX source from arXiv, when there is one. Headings, theorems and equations arrive exactly as written. A small LaTeX reader of my own pulls out sections, paragraphs, display maths and theorem-like blocks. The source is only trusted if its text maps back onto most of the PDF, which is also how each block gets its PDF page number.
  • Docling in a Cloudflare Container, for everything else. Docling is an open-source document converter that keeps layout, tables, headings and formulas. It needs more memory and time than a Worker has, so it runs in a container that sleeps when idle and wakes when a paper arrives.
  • Plain text as the fallback. If the container is busy, slow or down, the paper is read plain so the researcher is never stuck waiting, and it is marked as such. An hourly job later re-reads those papers precisely and swaps the passages in place.

The text is then cut into overlapping passages that never cross a page boundary, so every passage keeps an exact page number. Each passage is embedded with bge-m3 on Workers AI into Vectorize, and also written to a SQLite full-text index in a separate D1 database for keyword search.

3. Finding the right passages

When a question arrives, the job is to hand the answer model a small set of passages that contain the answer, and as little else as possible. One embedding search is not enough for that, so the pipeline has several stages.

Hybrid search

Dense vectors are good at meaning: "how does the virus persist between outbreaks" finds a passage about chronic infection even with no shared words. They are poor at exact terms: a gene name, a species, a named estimator, a symbol. Keyword search is the opposite. So every query runs both, in parallel: a bge-m3 search in the assistant's Vectorize namespace and a BM25 search over the full-text index. The visitor's text is reduced to quoted words before it reaches the full-text engine, so no search operator can be injected.

The ranked lists are merged with reciprocal rank fusion, which rewards a passage for ranking well in any list without needing the two kinds of score to be on the same scale.

Reranking

Embeddings compare a question and a passage that were each turned into numbers separately. A cross-encoder reads the two together and scores how well the passage answers the question, which is slower but much sharper. The top of the fused list goes to bge-reranker-base on Workers AI. If the reranker fails or times out, the fused order is used instead, so a slow component degrades the answer rather than breaking it.

Spreading across papers

Questions such as "how do these papers differ in their approach to X?" need passages from each paper involved. Left alone, the top of a ranked list is often filled by one paper. The final pick takes at most a few passages from any one paper and keeps some room for papers not yet represented. A relevance gate stops that rule from padding the context with papers that only share the topic: a passage competes for a slot only if its reranker score is close enough to the best one. Reranker scores bunch up near the top of their range when every paper is on a similar subject, so the gate compares them on a log-odds scale, where those differences are visible again. I calibrated it on a mathematician's real questions and checked it against the evaluation set described below.

Quick and Thorough

Visitors choose between two modes, on plans that include both. Quick searches with the question as asked. Thorough first asks a small, fast model on Groq to rewrite the question into extra search queries: one using the technical terms a paper would use, and one for any part of a multi-part question the first misses. The original question is always searched too, so a poor rewrite can add noise but never lose the visitor's own wording. The rewrite has a short time limit, and if it fails the search simply goes ahead with the question alone.

Follow-up questions

A follow-up such as "and what did the other paper find?" means nothing to a search index. When a question comes with earlier turns, the same small model condenses the conversation into one standalone question, which is what gets searched. The answer model still sees the conversation, so its reply reads naturally. A "New topic" button clears the thread.

4. Writing the answer

The chosen passages are grouped by paper, labelled with the paper and page, and placed in a prompt that tells the model to answer from them alone, to say when they don't cover the question, to cite only the labelled papers, and to keep notation consistent with the papers. Maths in the answer is rendered with a self-hosted copy of KaTeX, so the page's strict script policy still holds.

A frontier model, with two fallbacks

The answer is written by a frontier model. If that call fails, times out, comes back empty or declines to answer, the same prompt goes to the next model in the chain: gpt-oss-120b, an open-weight model, on Groq, and then the same model on Workers AI. All three calls go through Cloudflare's AI Gateway, which gives one place for logs, caching and provider keys, and lets me compare models on real traffic. Which chain an assistant gets is configuration, not code: every new assistant starts on the frontier model, and older ones are moving across after testing. Every answer is logged with the model that wrote it and any model that failed before it, so fallbacks are visible rather than silent.

I learnt to plan for this the hard way. In September 2026 the provider retired the model the original chat was hard-coded to, and every question returned an error until I fixed it. Since then no model name lives in code, there is always more than one model behind an answer, and a live end-to-end check asks real questions after every deploy.

Showing progress

A good answer from a strong model takes a few seconds, and a blank box for that long feels broken. The ask endpoint can reply as a stream of progress lines: first "searching the papers", then "writing from N papers" once the passages are chosen, then the finished answer. The widget shows these as a live status line. Clients that don't ask for the stream get a single JSON reply as before.

When the papers don't cover it

The model starts every reply with a status line saying whether the papers answered the question fully, partly or not at all. Code strips that line before the visitor sees anything. When the status is "not covered", the answer is the plain sentence “These papers don’t cover that.” and the retrieved passages are folded away, so a visitor isn't misled into reading loosely related passages as support. An earlier wording apologised at length and still listed the passages; people read that as a partial answer.

5. Citations you can check

A language model is very good at producing text that looks like a citation. That is not the same as a true one. Two rules keep citations honest.

  • The source list never passes through the model. The "Retrieved from" list under each answer is built in code from the metadata of the passages that were actually used, with the paper's title, year and the PDF page. The model cannot add a paper to it.
  • In-text citations are filtered. Papers cite other papers, so retrieved passages are full of author–year references to work that is not in the collection. After generation, a deterministic filter removes any bracketed citation that doesn't match one of the retrieved papers. An instruction in the prompt alone did not stop this; a check in code did.

Page numbers come from reading, not from the model: passages never cross a page, and LaTeX blocks are matched back to the PDF page they appear on. On the private library the page number is a link that opens the PDF at that page.

6. Cost, abuse and privacy

A spend ledger and guard

A frontier model costs real money per answer, and a free plan invites traffic I don't control. Every answer that a paid model writes is costed from its token counts and added to a monthly ledger in D1, kept per assistant, for the free plan as a whole, and overall. Before each answer the guard reads the ledger. Free assistants move to the cheaper open-weight chain well before any limit is reached, individually or as a group; past an overall ceiling, everyone does, and I get an email before that happens. The ledger is off the critical path: a failed read answers on the usual model, a failed write is logged and dropped, and no visitor ever waits on it.

Limits and bot checks

Questions are length-checked before anything else runs. Each client is rate limited per minute, keyed on the address Cloudflare's edge sets itself, so a caller can't choose it. Each plan has a monthly question allowance. Embeds also watch their daily traffic: a sudden spike, or a day over the assistant's ceiling, makes the widget ask for a Cloudflare Turnstile check before it answers, so a script hammering someone's embedded chat can't spend their allowance. Errors return a short fixed message and a request ID, never internal detail.

Private means private

Private library questions are sent to every model with AI Gateway's no-log and no-cache settings, and the Worker's own log line for them holds timings only: no question, no answer, no paper titles. Private papers live in their own namespace and are never searched for anyone else; the public side has no path into them. Stored PDFs are visible only to their owner and are deleted soon after the paper is removed.

7. How I know it works

"It gave a good answer when I tried it" is not evidence. Each change to retrieval or answering is run against fixed question sets before it ships.

  • Expected facts. Each answerable question lists short facts that are stated on a known page of a known paper, checked against the stored passages rather than from memory. A judge model grades whether the answer contains them, and the run also checks the right paper and page were cited.
  • Trap questions. Each set includes plausible questions on a neighbouring topic the papers don't cover. The only correct reply is "not covered". A system that answers these confidently is worse than one that misses a hard question.
  • Multi-paper questions. Some questions are marked as needing several papers, and the run flags any answer whose sources leave one out. This is what the spread step above was tuned against.
  • Latency per mode. Quick and Thorough are timed separately. The bar is a 95th-percentile answer time under about ten seconds; with the current frontier model both modes sit around eight seconds at the 95th percentile on a maths-heavy test set, with every trap question correctly declined.

Switching answer model is a decision, not a hunch. Before the change in October 2026 I ran a bake-off: the same saved contexts sent to each candidate model and effort level, graded by the same judge, timed, and costed per month at expected volume. The model that now answers was the best one that met the latency bar.

These sets are small, and I don't quote an accuracy percentage from them. What they reliably catch is regressions: a retrieval change that drops a paper, a prompt change that makes the model guess, a model that has become slow.

8. The earlier version

Ask My Papers grew out of a much smaller chat, Ask My Research, that I built for this site alone. It held six of my papers, about 780 plain-text chunks, embedded with bge-small-en-v1.5 on Workers AI and stored in Vectorize. Each question was embedded, the four nearest chunks were retrieved, and gpt-oss-120b on Groq, through AI Gateway, wrote an answer from them, with the same model on Workers AI as the fallback. It began life as a LangChain and Chroma prototype on a free host that slept when idle, then moved to a Cloudflare Worker with a median answer time of about a second and a half.

It worked for its purpose, and it taught me where the simple version stops:

  • plain text extraction broke maths, tables and section structure;
  • pure embedding search missed exact terms, and a fixed top four meant a question spanning several papers usually heard from one;
  • there was no way to say "not covered" cleanly, or to follow up on an answer;
  • and it was built for one person's papers. Other researchers asked for one of their own.

Ask My Papers is the answer to that list. The original code is still public on GitHub as a compact, readable example of a basic retrieval-augmented pipeline.
