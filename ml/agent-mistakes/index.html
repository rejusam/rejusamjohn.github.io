ML Explorer · Level 6 · Agents

Mistakes and limits

Agents go wrong in a few recognisable ways. See a made-up answer, a run going in circles and a tool error, what stops each one, and why a person should say yes before a tool that changes things.

About 10 minutes · Every trace is computed in your browser, apart from one tool-error case that is written in and labelled

Overview

In Memory a fact that dropped out of the window sent a run in circles. This lesson collects the ways a run can go wrong, and the safeguards that stop them.

Some failures end with no answer. Worse ones end with an answer that reads well and is not true. And some tools do more than read: they change things, and a change can be hard or impossible to undo.

You'll learn

  • four recognisable ways a run can go wrong
  • what an agent should do when a tool finds nothing, and what a tool error does
  • why to give a task only the tools it needs, and to ask a person before a tool that changes things

  1. Four ways to fail

    A run can go wrong in a few recognisable ways, and each one needs its own safeguard.

    The model on this page is a stand-in. Its choices come from fixed rules, listed in full in What is an agent?, and those rules never write a malformed call or a call to a tool that does not exist; a real agent makes its choices with a language model, which can write a wrong or malformed call.

    Four ways a run can go wrong:

    • A made-up answer: an answer that reads well but is backed by no fact the run found.
    • Going in circles: the same calls again and again, with no answer.
    • A tool error: a call the tool cannot carry out, for example because it cannot read the input.
    • The wrong tool, or one that does not exist: a real model can write either. The stand-in never does, so this page names the case but does not run it.

    The task: What food does kai like? Step 1 writes lookup("kai") and the result is "not found: kai". With the default instruction, "say so", the run is done after 2 steps: "I could not find kai." The next step shows what the other instructions do.

  2. Nothing found

    When lookup finds nothing, the instruction for that case sets what comes next.

    kai is not one of the 8 people in the invented world, so lookup returns "not found: kai". Rule R1 covers this case and has three settings. Pick one from the menu next to Run and Next message.

    say so: the answer is "I could not find kai.", after 2 steps. It is true, and plain.

    try again: step 2 writes lookup("kai") again. That cannot help: lookup gives the same text for the same input every time. The repeat check from The loop and when to stop stops the run after 2 steps, before the second call runs, so the loop ran lookup 1 time. With the check off, only the step limit of 8 would stop it.

    guess: this is what a careless loop does. The stand-in fills the gap with the first food in the food table, apples, and answers "kai likes apples." That answer is made up: kai is not in the world at all, so no food would be right. It reads just as well as a true answer; only the trace shows where it came from.

    A language model needs no guess rule to do this. It can write a plausible answer that nothing it was given supports, sometimes called a "hallucination". As in Large language models, in miniature: fluent is not the same as true.

  3. A tool error

    When a tool cannot carry out a call, the loop on this page stops.

    For the task "What is 3 × 1.25 + 2 × 0.8?" the stand-in writes calculator("3*1.25+2*0.8"), and the calculator returns 5.35. Its rules always write input the calculator can read.

    A language model writes a call as text, and text can come out malformed. So the trace in this step is a written-in example, not a run of the stand-in: the call calculator("2+"), cut short, as a real model could write it. No rule of the stand-in wrote it, so "Why this step" names no rule. The result row is what the calculator on this page really returns for that input: cannot read "2+".

    The loop on this page stops with "tool error" whenever a tool fails, apart from lookup's "not found", which is an ordinary result. Stopping means nothing is built on a broken result.

    Other loops give the error back to the model as a new message, so that it can write a corrected call. That can help, and it can also go in circles, which is one reason a step limit and a repeat check are still needed.

  4. Only the tools a task needs

    Give each task only the tools it needs, so a wrong call can reach less.

    The picture lists, for each of the 6 tasks in this level, the tools it needs. Here "needs" means the tools its run with the default settings writes calls for, or asks to use. No task's default run calls notepad.

    Of the 4 tools, calculator, lookup and notepad only read. send is different: it changes things, because it sends a message to someone.

    Run each task again with only its needed tools switched on, and the trace is the same, message for message: the other tools were never used. Pick a task from the menu to see its trace.

    Why it matters: a real model can write a call it should not, to a tool the task never needed. If the loop runs only the tools it was given, a call to any other tool cannot run. Fewer tools means fewer ways for a wrong call to do harm.

    The maths

    For each task, take the set of tools its default run writes calls for or asks to use:

    needs(task)={tools in the call and ask rows of its default run}\text{needs}(\text{task}) = \{\text{tools in the call and ask rows of its default run}\}needs(task)={tools in the call and ask rows of its default run}

    The union over the six tasks is calculator, lookup and send; notepad is in none of them. Giving a task exactly its set leaves every trace unchanged.

  5. Ask before changes

    Before a tool that changes things, the loop asks a person and waits for a yes.

    The task: Tell zoe what pears cost. Step 1 looks up pears. Step 2's plan line says the message is ready. With "ask before changes" on, R5 asks a person first, so the loop does not run send: it stops, waiting for a yes before send("zoe", "pears cost $1.10 each."). That is 2 steps. The model call that writes the ask counts as a step; waiting does not.

    Use the buttons next to Run and Next message.

    • Approve: the loop runs send, then step 3 answers "Told zoe: pears cost $1.10 each." The sent list holds 1 message, with the price $1.10. 3 steps.
    • Decline: nothing is sent, and the run stops as declined after 2 steps.
    • Switch off ask before changes: it sends without asking, done after 3 steps.

    On this page send only records the message in the list under the picture; nothing leaves the page.

    Why ask: a reading tool can run again with no harm, but a message, once sent, cannot be unsent. The same holds for tools that pay, delete or book. A person's yes before such a tool is the last check before a wrong call becomes a real change.

  6. What the safeguards stopped

    Each safeguard on this page stopped one kind of failure. None of them makes a run correct.

    Across the runs on this page there were 5 different ways to stop: done, repeated call, tool error, waiting for approval and declined. The picture lists what each safeguard did. Pick any run of this lesson from the menu to see its trace and which safeguard, if any, stopped it.

    • The instruction "say so": a plain "I could not find kai." instead of a made-up answer.
    • The repeat check: stopped the second, identical lookup.
    • Stopping on a tool error: nothing was built on the reply cannot read "2+".
    • Asking before changes: nothing was sent without a yes.
    • Only the needed tools: no stop of its own; it limits what a wrong call can reach.

    No safeguard caught the guess: "kai likes apples." ended as done, like a true answer. Only the instruction prevents it. Real agents add many more safeguards, and still go wrong in these ways.

Quick check

The lookup finds nothing. Which instruction is safest?

Right. The run is done after 2 steps with "I could not find kai.": true, and plain.

lookup gives the same text for the same input every time, so looking again cannot help. The repeat check stopped the run after 2 steps with no answer.

"kai likes apples." is made up: kai is not in the invented world. It reads like a true answer, and no safeguard stopped it.

Why ask a person before "send"?

Right. A reading tool such as lookup can run again with no harm. After a no, the run stopped as declined and nothing was sent.

Speed has nothing to do with it; on this page send only records the message. The ask is there because a change may not be undoable.

The message was right: pears cost $1.10. The ask is there for the times a message is wrong, since once sent it could not be taken back.

Asking saves no steps. Approved, the run takes 3 steps, the same as with ask before changes off (3).

Lesson complete

  • Runs go wrong in recognisable ways: a made-up answer, going in circles, a tool error, the wrong tool.
  • When a tool finds nothing, "say so" gives a true answer; a guess gives a made-up one that reads just as well.
  • Give a task only the tools it needs, and ask a person before a tool that changes things.

Common misconceptions

  • "An answer that reads well was found." "kai likes apples." was made up, and ended as done.
  • "Trying again fixes a lookup that found nothing." The same input gives the same result; the repeat check stopped it.
  • "Asking a person costs extra model calls." Approved, the run took 3 steps, the same as without asking.

  2. Yao et al., "ReAct: Synergizing Reasoning and Acting in Language Models", arXiv 2210.03629 (2022), in which a language model writes short free-text steps in between actions such as searches, and is given each action's result before the next.
  3. Schick et al., "Toolformer: Language Models Can Teach Themselves to Use Tools", arXiv 2302.04761 (2023), in which a language model is trained to write calls to tools, among them a calculator and search engines, inside its own text, and to use their results.
