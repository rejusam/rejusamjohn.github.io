Mistakes and limits

Agents go wrong in a few recognisable ways: a made-up answer, a run going in circles, a tool error. Each one has its own safeguard. A person should also say yes before a tool that changes things runs.

About 10 minutes · Every trace is computed in your browser, apart from one tool-error case that is written in and labelled

Overview

In Memory a fact that dropped out of the window sent a run in circles. This lesson collects the ways a run can go wrong, and the safeguards that stop them.

Some failures end with no answer. Worse ones end with an answer that reads well and is not true. And some tools do more than read: they change things, and a change can be hard or impossible to undo.

You'll learn

  • four recognisable ways a run can go wrong
  • what an agent should do when a tool finds nothing, and what a tool error does
  • why to give a task only the tools it needs, and to ask a person before a tool that changes things

  1. Four ways to fail

    In Memory a lost fact sent a run in circles. That is one of four ways a run can go wrong.

    Look at the picture: one box per way to go wrong, with the step that shows it. The dashed one is only named.

    The trace shows a run that goes right. The task: What food does kai like? Step 1 writes lookup("kai") and gets "not found: kai". With the default instruction, "say so", the run is done after 2 steps: "I could not find kai."

    Note: the model here is a stand-in that follows fixed rules (see What is an agent?). They never write a broken call, or call a tool that does not exist. A real model can write a wrong call, so that case is only named.

  2. When lookup finds nothing

    Same task, same "not found". Now try the other two instructions.

    Look at the picture: the three instructions, and how each run ends. Pick one by the "Run" button.

    say so: done after 2 steps: "I could not find kai." True, and plain.

    try again: step 2 writes lookup("kai") again. Same input, same result. The repeat check, which stops a call identical to the one before, ends the run after 2 steps.

    guess: the stand-in answers with the first food in the food table: "kai likes apples." It is made up, yet reads like a true answer.

    Note: a real model needs no guess rule to write an answer that nothing backs up.

    The maths

    The three instructions are settings of rule 1 of the six, shown as R1 in the "Why this step" box. kai is not one of the 8 people in the invented world, so no food would be right. The guess is the first food in the world's food table, apples; only the trace shows where it came from.

    With "try again", the repeat check from The loop and when to stop stops the run before the second call runs, so lookup ran 1 time. With the check off, only the step limit of 8 would stop it.

    A made-up answer from a language model is sometimes called a "hallucination". As in Large language models, in miniature: fluent is not the same as true.

  3. A tool error

    Next, a different failure: a call the tool cannot carry out. The loop on this page stops.

    Look at the picture: a tool call, its result, and the loop stopping. It is a written-in example, not a run of the stand-in.

    For "What is 3 × 1.25 + 2 × 0.8?" the stand-in writes calculator("3*1.25+2*0.8") and gets 5.35. It never writes a call the calculator cannot read.

    A real model can write a call cut short, like calculator("2+"). The calculator here replies cannot read "2+".

    The loop on this page stops when a tool fails (lookup's "not found" is not a failure). So nothing is built on a broken result.

    Note: other loops hand the error back to the model. That can help, or go in circles.

  4. Only the tools a task needs

    A wrong call does less harm if it can reach less. So give each task only the tools it needs.

    Look at the picture: the tools each of the 6 tasks calls in its default run, or asks to use. Pick a task from the "task" menu to see its trace.

    No task calls notepad. Of the 4 tools, calculator and lookup only read, and notepad only writes the run's own notes. send changes things: it sends a message.

    With only its own tools on, each task's trace is the same as with all four. If the loop runs only the tools it was given, a wrong call to any other tool cannot run.

    The maths

    For each task, take the set of tools its default run writes calls for or asks to use:

    needs(task)={tools in the call rows and ‘Waiting for your yes’ rows of its default run}\text{needs}(\text{task}) = \{\text{tools in the call rows and `Waiting for your yes' rows of its default run}\}needs(task)={tools in the call rows and ‘Waiting for your yes’ rows of its default run}

    The union over the 6 tasks is calculator, lookup and send; notepad is in none of them. Giving a task exactly its set leaves every trace unchanged.

  5. Ask before sending

    send changes things. So before it runs, the loop asks a person for a yes.

    Look at the picture: the ask, the answers and the sent list.

    The task: Tell zoe what pears cost. Step 1 looks up pears. Step 2 writes an ask, not the send call, as "ask before changes" is on (rule 5 of the six). The run stops after 2 steps, at "Waiting for your yes".

    Try the buttons by the "Run" button:

    • Approve: send runs; step 3 answers "Told zoe: pears cost $1.10 each."
    • Decline: nothing sent; stopped as declined after 2 steps.
    • Untick "ask before changes": no ask; send runs.

    Why ask: a sent message cannot be unsent.

    The maths

    Steps count model calls. The call that writes the ask is step 2; waiting for the answer is not a step. After a yes, the loop runs send and step 3 writes the answer: 3 steps. With "ask before changes" off it is also 3 steps, so asking costs no model call.

    The ask in full: a yes before send("zoe", "pears cost $1.10 each."). After a yes the sent list holds 1 message. On this page send only records the message; nothing leaves the page.

    A lookup can run again with no harm. A yes helps only if the person reads the call first. The same reason to ask holds for tools that pay, delete or book: once done, they may not be undoable.

  6. What the safeguards did

    Last, all the runs together. No safeguard makes a run correct.

    Look at the picture: what each safeguard did. Pick a run from the "run" menu; its safeguard, if any, is outlined. Runs ended in 5 ways.

    • "say so": a plain "I could not find kai."
    • Repeat check: stopped the repeated lookup.
    • Stop on a tool error: nothing built on cannot read "2+".
    • Ask before changes: nothing sent without a yes.
    • Only the needed tools: limits what a wrong call can reach.

    No safeguard caught the guess: "kai likes apples." ended as done.

    Note: for a real model, even "say so" cannot rule out a made-up answer.

Quick check

The lookup finds nothing. Which instruction is safest?

Right. The run is done after 2 steps with "I could not find kai.": true, and plain.

lookup gives the same text for the same input every time, so looking again cannot help. The repeat check stopped the run after 2 steps with no answer.

"kai likes apples." is made up: kai is not in the invented world. It reads like a true answer, and no safeguard stopped it.

Why ask a person before "send"?

Right. A reading tool such as lookup can run again with no harm. After a no, the run stopped as declined and nothing was sent.

Speed has nothing to do with it; on this page send only records the message. The ask is there because a change may not be undoable.

The message was right: pears cost $1.10. The ask is there for the times a message is wrong, since once sent it could not be taken back.

Asking saves no steps. Approved, the run takes 3 steps, the same as with ask before changes off (3).

Lesson complete

  • Runs go wrong in recognisable ways: a made-up answer, going in circles, a tool error, the wrong tool.
  • When a tool finds nothing, "say so" gives a true answer; a guess gives a made-up one that reads just as well.
  • Give a task only the tools it needs, and ask a person before a tool that changes things.

Common misconceptions

  • "An answer that reads well was found." "kai likes apples." was made up, and ended as done.
  • "Trying again fixes a lookup that found nothing." The same input gives the same result; the repeat check stopped it.
  • "Asking a person costs extra model calls." Approved, the run took 3 steps, the same as without asking.

Further reading

  1. Russell & Norvig, Artificial Intelligence: A Modern Approach (4th ed.), Chapter 2, "Intelligent Agents": agents in general, well beyond language models.
  2. Yao et al., "ReAct: Synergizing Reasoning and Acting in Language Models", arXiv 2210.03629 (2022), in which a language model writes short free-text steps in between actions such as searches, and is given each action's result before the next.
  3. Schick et al., "Toolformer: Language Models Can Teach Themselves to Use Tools", arXiv 2302.04761 (2023), in which a language model is trained to write calls to tools, among them a calculator and search engines, inside its own text, and to use their results.
