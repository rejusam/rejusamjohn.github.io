The loop and when to stop

A loop runs until something stops it. See three ways a run stops, what a step costs, and why a long chain of steps fails more often than a short one.

About 10 minutes · Every trace, count and chance is computed in your browser; the formulas are in The maths

Overview

In Tools the loop ran each call the model wrote and went round again. This lesson is about the other end: how the loop stops.

The runs on this page stop in one of three ways. The model writes an answer, and the run is done. The loop counts the steps and stops at a step limit. Or the loop finds the same tool call twice in a row and stops it. Each step is one call to the model, and each step can go wrong, so how many steps a run takes matters twice.

You'll learn

  • three ways a run stops: an answer, a step limit and a repeat check
  • that every step is a model call, so a run going in circles still costs
  • why a long run fails more often, and how to work out by how much

  1. Why stop at all

    The loop goes round until something stops it. If nothing does, it never ends, and every turn is another model call.

    The model on this page is a stand-in. On this page the choices come from fixed rules, listed in full in What is an agent?; a real agent makes them with a language model, which can write a wrong or malformed call.

    The picture shows the loop. Each time round, the loop checks the step limit, calls the model once (one step), and stops if the model wrote an answer. If the model wrote a call, the loop checks that it is not the same as the call just before it, runs the tool and goes round again. The three ways out used in this lesson are on the right. A tool that fails is another way out, and so is waiting for a person's yes; both are in the lesson on mistakes and limits.

    The trace is the eli task from the last lessons: eli buys 4 of the food eli likes. What does that cost? Select a row: the picture marks the part of the loop it came from.

  2. Done: the answer ends the loop

    The usual way out: the model writes an answer instead of a call, and the loop stops.

    On each step the stand-in writes a plan line and then either a tool call or an answer. A call goes to the loop, which runs the tool and goes round again. An answer ends the run, and the stop reason is "done".

    In the eli task the first 3 steps each call a tool. Step 4 writes the answer "That costs $5.00.", and the loop stops.

    A real model chooses when to write its answer, and it can answer too early or keep writing calls. That is why the loop needs the other two ways out.

    The maths

    The loop is a function from the messages so far to the next action. Write hth_tht​ for the messages after ttt steps. The next action is

    at+1=model(ht)a_{t+1} = \text{model}(h_t)at+1​=model(ht​)

    If at+1a_{t+1}at+1​ is an answer, the loop stops. If it is a call, the loop runs the tool, and ht+1h_{t+1}ht+1​ is hth_tht​ with the plan line, the call and its result added.

  3. A step limit

    The loop counts the steps and stops at a limit, whether or not there is an answer yet.

    Move the step limit slider, next to Run and Next message. The eli task needs 4 steps. With a limit below that, the step limit stops the run and there is no answer. At a limit of 3, the last result is 5, the very number the task asks for, but the step that would write the answer never comes.

    With a limit of 4 or more, the run is done after 4 steps, however high the limit. The loop checks the limit before each model call; the other runs on this page use a limit of 8.

    A limit that is too low stops a run that would have worked. A limit that is too high lets a stuck run make more calls before it stops.

    The maths

    With a step limit LLL, the loop stops before the next model call once t=Lt = Lt=L. A run that needs nnn steps gets its answer only if

    L≥nL \ge nL≥n

  4. Going in circles

    A run can repeat itself and never answer. A repeat check stops it early.

    The task: What food does kai like? kai is not in the invented world, so lookup returns "not found: kai". On this step the stand-in is set to try the same lookup again when a lookup finds nothing, one of the settings of R1.

    With the repeat check on, step 1 writes lookup("kai") and gets "not found". Step 2 writes the same call again. The loop compares it with the call just before it, finds them the same, and stops with "repeated call" without running it: 2 steps, 1 tool run. Its plan lines apply R3 and R1.

    Switch the repeat check off. Now nothing but the step limit stops the run: it writes the same lookup on every step and stops at the limit after 8 steps, with 8 tool runs and no answer.

    The check here only compares a call with the one just before it. A run that alternates between two calls (A, B, A, B, …) passes it every time, and only the step limit stops it. The lesson on memory has such a run.

  5. Every step can go wrong

    In the simplest picture, a run works only if every step works. The more steps, the more chances for one of them to go wrong.

    Say each step succeeds with chance p, a number between 0 and 1, and a run needs k steps. If the steps succeed or fail independently of each other, the chance that all k succeed is p multiplied by itself k times: p to the power k.

    With p = 0.95, 10 steps all succeed with chance 0.60. The eli task's 4 steps would all succeed with chance 0.81. Move the p slider: the line shows the chance for each k, and the dashed line marks 0.5.

    This is a simplification. It assumes the steps are independent, and in a real run they are not: a wrong fact in an early step can spoil every later one, and a later step can sometimes catch an earlier mistake. The stand-in's steps never fail at random at all; its rules give the same trace every time. Here p is meant as the chance that one step of a real model's run succeeds.

    The maths

    If each of kkk independent steps succeeds with chance ppp,

    P(all k succeed)=pkP(\text{all } k \text{ succeed}) = p^kP(all k succeed)=pk

    For the chance to stay at or above a target, take logs. For ppp between 0 and 1 (not equal to 1), log⁡p<0\log p < 0logp<0, so dividing by it flips the inequality:

    pk≥target  ⟺  k≤log⁡(target)log⁡pp^k \ge \text{target} \iff k \le \frac{\log(\text{target})}{\log p}pk≥target⟺k≤logplog(target)​

    With ppp = 0.95 and a target of 0.5, the right side is 13.51, so up to 13 steps: the chance is 0.51 at 13 steps and 0.49 at 14.

  6. Every step is a model call

    One step is one call to the model. A run that goes in circles still pays for every turn.

    In each step the model is given the messages and writes a plan line and an action. Running a tool is not a model call: the loop does that. Pick a run from the run menu. The picture shows one box per model call, and under it the tool run that call led to.

    • the eli task, step limit 8: 4 model calls, 3 tool runs, answered
    • the eli task, step limit 3: 3 model calls, 3 tool runs, stopped by the step limit
    • the kai task, repeat check on: 2 model calls, 1 tool run, stopped by the repeat check
    • the kai task, repeat check off: 8 model calls, 8 tool runs, stopped by the step limit

    With the repeat check off, the kai task makes 6 more model calls than with it on, and still has no answer. For a real language model, each call takes time and computing; the step limit caps how many a run can make.

    The maths

    Each step is one model call. On this page a step writes at most one tool call, and an answer step writes none, so

    model calls=steps≥tool runs\text{model calls} = \text{steps} \ge \text{tool runs}model calls=steps≥tool runs

    Write nnn for the number of steps a task needs to answer and LLL for the step limit. For the runs on this page that the repeat check does not stop,

    model calls=min⁡(n,L)\text{model calls} = \min(n, L)model calls=min(n,L)

    The kai run with the repeat check off never answers, so it makes LLL calls: 8. With the check on it stops after 2.

Quick check

What does a step limit protect against?

Right. With the repeat check off, the kai run writes the same call on every step; the step limit stopped it after 8 steps.

The limit does not look at answers. A wrong answer written within the limit ends the run as "done", like a right one.

A tool error is a different way out, shown in the lesson on mistakes and limits. The step limit only counts steps.

The limit counts model calls, not time. A slow tool does not add steps.

Each step succeeds with chance 0.9, independently. What is the chance that all 10 steps succeed?

Right. 0.9 multiplied by itself 10 times is about 0.35: the run fails more often than not.

That is the chance for one step. All 10 must succeed, so 0.9 is multiplied by itself 10 times.

That is 0.9 times 10, and a chance is never more than 1. Chances of independent steps multiply with each other.

That is the chance that one given step fails, not the chance that all of them succeed.

Lesson complete

  • This lesson showed three ways out: an answer (done), a step limit, and a check for the same tool call twice in a row.
  • Every step is one model call, whether or not the run gets anywhere; tool runs are done by the loop.
  • If each step succeeds with chance p, independently, all k succeed with chance p to the power k: 0.60 for 10 steps at p = 0.95.

Common misconceptions

  • "A higher step limit gives better answers." Any limit from 4 up gives the eli task the same answer in the same number of steps. A higher limit only lets a stuck run make more calls.
  • "A repeat check catches every loop." This one compares a call only with the one just before it; two calls taken in turn get past it.
  • "A step that succeeds with chance 0.95 is good enough." 10 such steps in a row all succeed with chance 0.60.
